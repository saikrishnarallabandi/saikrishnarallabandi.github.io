Judith answers in my family's group chat.

She is a personal AI agent that has run continuously for one user since June 2026 — across WhatsApp threads, email, a job runner and a pair of smart glasses. This page is not about the model. It is about the layer wrapped around her: twenty-one plugins that decide what is safe to act on, what is worth remembering, and what is allowed to reach a human being.

An assistant for one person is a feature. An assistant in a room full of people is a different problem.

Judith does not sit behind a chat box waiting to be opened. She is already in the thread. That single change turns ordinary assistant problems into questions about other people: who is allowed to steer her, whose information she is holding, and whether an answer that is correct is also an answer that should be said out loud.

Group threads

She replies in WhatsApp conversations where more than one person can see her, and anyone present can try to redirect her.

Smart glasses

The same agent, speaking only to me. Here she is allowed to start the conversation, because the audience is one person.

Background work

Scheduled wakes, mail, health signals and a job board that runs while nobody is asking her anything.

One message, end to end.

A turn is not a single call to a model. It is a sequence of stages, and a plugin can attach to any of them. Four stages can stop or rewrite what happens; the rest only observe and write down what they saw. Stages that return a decision run in order of priority, shown after each name.

The four marked stages are the only places anything can be blocked or rewritten. Everything else is a record. That distinction is the whole design: a stage that writes nothing down cannot be blamed for anything later.

Each plugin owns exactly one invariant.

The rule is narrow on purpose. One plugin holds one promise — small enough that when it breaks, the break can be named, tested and undone without touching anything else. What the rule buys is attribution. When something goes wrong, the answer should be a specific stage that made a specific decision, not "the model didn't work."

The plugins carry Sanskrit names, which is not decoration: jataayu is the bird that fought to protect someone in flight, smriti is memory, sakshi is the witness, drishti is sight. Each name is the invariant.

What a plugin actually is.

Two files. A manifest that can be read without running any of the plugin's code, so the system can check its configuration and find out which tools it owns before loading it, and a module that exports a single setup function.

// the manifest, abridged
{
  "id": "disha",
  "name": "Disha Model Router",
  "activation": { "onStartup": true },
  "contracts": { "tools": ["disha_route", "disha_gate"] },
  "configSchema": { "additionalProperties": false, … }
}

One setting bites harder than it looks. Because unknown keys are refused, a single misspelled option rejects the whole configuration reload — and the plugin keeps running quietly on its previous settings rather than telling anyone.

Everything a plugin can do, it does through one object handed to that setup function: attach to a stage, register a tool, read its own settings, write to the log.

There is one genuinely dangerous trap here. Two methods on that object have almost the same name, and only one of them is ever called during a conversation. Register with the wrong one and the plugin loads, reports no error, appears in the inspector — and is never invoked. It looks completely healthy and does nothing.

What a plugin may do is decided by the stage it attaches to.

Seven patterns cover all twenty-one. They are not ranks or steps; they are different jobs.

Adding context

situation · avastha · state-injector · heartbeat-focus

Attach before the prompt is assembled and hand back a block of text to put in front of it. Read what this example refuses to do: stale information is dropped rather than passed off as current, a turn it cannot attribute to a person gets nothing at all, and it never throws an error into a live conversation.

api.on("before_prompt_build", async (_event, ctx) => {
  try {
    // Gate on the PERSON, not the agent id. When the per-person
    // bindings collapsed into one agent, that id became a constant
    // and this check passed for EVERY direct message.
    if (!isOwnerTurn(ctx, { expect: ownerAgentId })) return undefined;
    if (isSharedOrPublicCtx(ctx))                    return undefined;
    const block = readSituationBlock(filePath, staleMs, Date.now());
    if (!block)                                     return undefined;
    return { prependContext: block };
  } catch (_) {
    return undefined; // live path: never throw
  }
});

Stopping things

jataayu, with seven submodules

Return a verdict. Blocking ends the turn; anything else lets it continue. Note the last few lines: if the guard itself breaks, it lets the message through. A fault in a safety check must not be able to silence the assistant.

if (risk === "HIGH" && blockOnInboundHigh) {
  return {
    outcome:  "block",
    reason:   `HIGH prompt-injection risk — ${reason}`,
    message:  "Blocked by the guard: this looks like an injection attempt.",
    category: "prompt-injection",
  };
}
return { outcome: "pass" };
} catch (e) {
  console.error(`gate error, failing open: ${e.message}`);
  return { outcome: "pass" };
}

plugins/jataayu/index.js:594–607

Two decisions inside this guard are worth pulling out. It decides whether a message came from me by looking only at who sent it, never at what the message says — otherwise anyone could paste my name into a message and inherit my permissions. And it keeps an explicit list of what each tool really does, because the underlying library treats anything it does not recognise as harmless reading. Under that default, the command that edits files and the command that writes to memory were both classified as reads.

Offering a tool

gmail · health · sangraha · maestro · upaya · keenable · linkedin

Register a tool and keep no rules inside it. These are thin wrappers that hand the real work to a shared Python program, so the command line, the scheduled jobs, the tests and the assistant all run one copy of the logic instead of four that drift apart.

Keeping records

sakshi · lane-watchdog · inbound-ledger

Attach, return nothing, write a row. This is the least glamorous kind and the one everything else depends on: the failure rates above exist only because these plugins wrote them down. Where a plugin keeps no record, its promise cannot be checked at all.

Handing off

sarathi, currently switched off

Take a turn and pass it to a separate session. It is deliberately given a low priority so the safety checks settle first — whoever claims a turn first keeps it, and a message the guard would have refused must never reach the part that delegates.

Serving a page

drishti

Offer a web route instead of a tool. Drishti is the job board: every run, why it failed, and a button to run it again.

Holding memory

smriti

Facts, each with a record of where it came from, which can be replaced by a better version or quarantined when it looks wrong. Currently 6,175 facts across 13 separate namespaces, with 1,093 recorded links between a fact and the one that replaced it. Memories are formed at the end of a turn, not during it.

All twenty-one, and whether they are actually running.

Being installed is not the same as being loaded. A plugin has to be on a scanned path, on the permitted list, and switched on. Miss any one and it sits on disk doing nothing, with no warning printed anywhere. The states below were read from the running system rather than from its documentation, which disagrees.

Three ways the design failed.

Where a plugin keeps a record, the rule does what it promised. Last-mile checks caught 65 leaks — 44 raw data structures and 21 pieces of internal machinery — that would otherwise have been sent to a person. But the failures are the more useful half of the result, and none of them was anticipated.

Separating a promise out does not put it into effect.

The check that decides whether a tool is allowed to act is designed, written, deployed and running — in observe-only mode. All 544 of its recorded decisions were rehearsals. The protection the architecture appears to offer is not the protection actually in force, and nothing in the diagram says so.

It does not keep the promise alive.

One plugin is sitting on disk, identical to its source, listed as healthy by the tool that checks for tampering — and has never once been loaded, because it was left off the permitted list. The checker was only ever asking whether the file had changed, not whether anyone was running it.

It does not measure the promise.

Several plugins keep no record at all. Their promises cannot be shown to have held or broken, which means that for those parts of the system the architecture cannot answer the one question it was built to answer.

Drawn from 57 days of recorded operation: 77,919 steps, 37 completed self-improvement cycles, 2,026 messages she started herself, and a 6,175-fact memory. Every figure here is regenerated from the live system by a single command, which is the only reason I trust the unflattering ones.

The same agent, in a room of one.

On the glasses Judith is allowed to speak first, because only one person can hear her. Everything else is unchanged: gather the context, decide whether this moment is worth interrupting, and send the answer only to the person entitled to it. The rule that governs a group thread is the same rule; the room is what changed.
