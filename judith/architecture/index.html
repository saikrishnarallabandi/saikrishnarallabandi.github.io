How the layer around Judith works.

Engineering detail for the layer wrapped around Judith. The lifecycle of a single message, the ten named components and what each one promises, and the three ways the design failed. Written from the source, so it reads like a specification.

One message, end to end.

A turn is not a single call to a model. It is a sequence of stages, and a component can attach to any of them. Four stages can stop or rewrite what happens; the rest only watch and write down what they saw.

The four marked stages are the only places anything can be stopped or changed. Everything else is a record. That distinction is the whole design: a stage that writes nothing down cannot be held responsible for anything later.

Each component keeps exactly one promise.

The promise is narrow on purpose — small enough that when it breaks, the break can be named, tested and undone without disturbing anything else. What that buys is attribution. When something goes wrong, the answer should be a particular stage that made a particular decision, not "the model didn't work."

The first two numbers are the case for the rule: an average across every tool describes none of them, and splitting by the component that owns each call is what makes a failure rate mean anything. The third is the case against trusting it too far. Those 55 commands returned command not found and were still logged as successful, because what gets recorded is whether the tool wrapper raised an error, not whether the command did what it was asked. Roughly a thousand more carry a missing file or a stack trace in the same shape.

So the honest version of the claim is narrower than the one I set out to make: one promise per component buys attribution at the stages that write a decision down, and only for the failures that stage's own idea of success can see.

The ten named components, and whether they are actually running.

Being installed is not the same as being loaded. A component has to be on a scanned path, on the permitted list, and switched on. Miss any one and it sits on disk doing nothing, with no warning printed anywhere. The states below were read from the running system rather than from its documentation, which disagrees.

Smriti is the largest of them: 6,175 facts across 13 separate namespaces, each able to be replaced by a better version or quarantined when it looks wrong, with 1,093 recorded links between a fact and the one that superseded it. Memories are formed at the end of a turn, not during it.

Three ways the design failed.

Where a component keeps a record, the rule does what it promised. The last check before anything reaches a person caught 65 leaks — 44 raw data structures and 21 pieces of internal machinery. But the failures are the more useful half of the result, and none of them was anticipated.

Separating a promise out does not put it into effect.

The check that decides whether a tool is allowed to act has recorded nothing at all. Not one decision. The 544 entries in its ledger were written by a different part of jataayu upstream, which is itself set to observe-only — and because that part never marks a turn as suspect, the check downstream sees nothing worth examining and returns before it writes anything. Two pieces, each configured separately, each behaving exactly as told. Between them, a gate that appears in every diagram and has never once run.

It does not keep the promise alive.

Disha sits on disk, byte-for-byte identical to its source, and has never once been loaded, because it was left off the permitted list. Worse is what happened to the alarm. The drift checker is correct: run it now and it reports the mismatch and exits with an error. But the thing that was supposed to run it every thirty minutes never calls it — the wiring described in its own header comment does not exist. The health log has been printing 0 problems | all OK every half hour, next to a fault that has stood since the first of September.

It does not measure the promise.

Several components keep no record at all. Their promises cannot be shown to have held or broken, which means that for those parts of the system the architecture cannot answer the one question it was built to answer.
